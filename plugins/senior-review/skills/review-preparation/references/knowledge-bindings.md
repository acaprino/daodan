# Knowledge bindings

Use the skill inventory actually available in the host. Keep the same candidate snapshot,
project/worktree and run identity. A generated registry is not installation
evidence. Normalize the actual host/project inventory and preserve its
availability provenance. If no inventory mechanism exists, declare knowledge
selection unavailable rather than inferring installed skills. Methods, workflow
wrappers and role wrappers are not automatic review knowledge. An unclassified
relevant match is a classification gap.

Derive one scope per affected package/behavior boundary. Record exact target paths,
languages, used frameworks, topics and code/configuration activation evidence.
Include relevant embedded SQL or cross-language calls when the actual candidate
shows them. Root dependencies from unrelated monorepo packages do not activate
knowledge. Search metadata as needed to discover useful labels, then refine the
evidence-backed scope signals. Search ranking is a lead, not a coverage gate.

Map knowledge dimensions to the existing selected native delivery IDs in each
scope's `workers` field: correctness to the code lens, security to security,
performance to the applicable performance lens, data-integrity to persistence,
resource-lifecycle to ownership, test-quality to the test lens, and other dimensions
to their actual owner. The mapping is about review risks, never a language registry.
Assign every selected dimension explicitly, including several dimensions owned by
one lens. Preparation preserves `dimension_workers`; an unassigned dimension is
failed coverage and cannot be hidden by another assigned dimension.
Use the full existing role brief. Where no selected lens owns a relevant domain
question, add one task-specific lens through the already declared host
isolated-worker binding, with its scope, budget and assigned report path. If no
such binding exists, declare the task-specific lens unavailable. That worker
applies selected knowledge; it never substitutes for a failed mandatory canonical
specialist or dispatches a new undeclared role. Respect explicit reviewer
selection and budgets; declare excluded coverage rather than silently expanding it.

When the host provides a catalog preparation mechanism, run it with
operation=review after assigning all selected knowledge to worker delivery IDs.
Otherwise write the validated selection result directly as
`knowledge/selection.json` in this run and declare that canonical catalog
validation was unavailable. `knowledge_selection` carries that path and selection
fingerprint in the native brief/selection. Each native reviewer binding records
`knowledge_ids` (empty when none) for its own scope/lens. A knowledge input is
selected once, with one or more scoped worker assignments. Preparation hashing
does not prove worker reading. Do not create one reviewer per skill, repeat
preparation or run specialist workflows.

No React, TypeScript or platform specialist exists. Record their activation signals and
leave the missing specialist coverage explicit until senior-review owns equivalent
micro skills. General review lenses may still inspect the same evidence, but they
cannot silently replace a missing specialist. Keep automatic activation, explicit
overrides, independent inputs and report rules.

Before dispatch, validate target and knowledge bindings together. A selected load
failure is failed coverage; any candidate gate requiring it cannot pass. Unmatched,
unknown or unresolved scope signals remain declared gaps. A report may deliver that
degraded coverage but must not claim those domains were verified. Use the same
selection through lifecycle change/repair/verify, never a branch substitute.
