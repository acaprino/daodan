# Evidence-aware documentation writing

Write for the file's planned reader and purpose. Calibrate framing and depth with
audience-adaptation.md, preserving the source author's intentional voice.
Structure belongs here; voice editing belongs to the text-humanizer method.

Use an entry point, conceptual overview, relevant how-to and reference where they
help the reader. Omit unnecessary layers, empty headings and diagrams. Templates
describe possibilities, never minimum file, line, question or diagram counts.

Each factual implementation claim cites current source. Keep detailed locators
in hidden Markdown comments or a reference section when that improves readability;
do not erase provenance from the operational report. Public API reference may
show file:line directly. Intended behavior and rationale cite approved decisions
or requirements; observable code alone does not establish them.

Keep examples complete enough for their purpose and grounded in project scripts,
configuration or meaningful tests. Say when they were not executed. Preserve
tables, quantities, certainty and obligations. Avoid copying a mutable fact to
many owners; link to its canonical source and update all necessary echoes together.

Use the project's existing relative links and documentation framework. Explain
unknowns without filling them with a plausible story. Add open questions only
when observed evidence creates a real gap. No quota of questions is required.
