## Composition and execution contracts

The compiler resolves `[reviewers.compositions.<role>]` from each provider's
existing manifest. Members use canonical registered identities. The same DAG
resolver supplies native roles, inline dispatch, catalog entries and provenance;
there is no second prompt registry. It rejects unknown or duplicate direct members,
cycles, undeclared providers, incompatible models and process-role absorption.
First occurrence deduplicates leaves reached through different nested presets.
Each member retains its provider references and operation restrictions.

The 13 preserved broad identities cover security, data integrity, distributed
flow, performance, operability, accessibility, cleanup, general code review,
testing, React, TypeScript, platform engineering and abstraction. Their checks
come from canonical leaves rather than a second handwritten review prompt.

The preparation helper composes candidate-bound obligations into jobs using
verified provider versions, installed bodies, scopes, knowledge fingerprints and
permissions. It preserves distinct scopes and independent modes. Common
instructions appear once per job. A context limit splits branch jobs or fails;
it never drops required checks. Light review retains exactly one discovery job.
The helper creates no worker and makes no model call.

All new review preparations validate jobs before dispatch. The roster supplies
coverage obligations and support permissions, not another worker list. The host
receives the actual isolated-worker role and job body once each, with separate
provider bindings. The coordinator checks every expected job and member outcome
against candidate and body fingerprints. Missing or failed coverage blocks
completion. Blind discovery, verification lenses and critic keep separate inputs,
contexts and deliveries. Historical records remain readable under their original
contract; continuation of stale or unprepared work needs a fresh immutable entry.

The conservative code floor retains source validation, resource lifetime,
algorithmic cost, security, persistent state, startup ordering, temporal and
distributed behavior, API contracts and test reliability. Missing or stale graph
information cannot remove them. Narrowing needs candidate/scope-bound evidence;
explicit required receiving obligations and core local checks survive. React
Server Actions, offline merge policy and client authority are covered by explicit
cross-provider receiving obligations, rather than a note alone.
