# Minimal complete changes

## Decision and scope

Integrate the approved Ponytail-inspired guidelines into Daodan's existing owners.
Keep the shared discipline in project-protocol and the repository bootstrap;
complete change scope belongs to project-lifecycle, implementation to the stack
writers, and meaningful test protection to testing. Project-knowledge's two
instruction templates carry the same protocol-owned working rule for generated
project guidance, as enforced by the existing fact anchor. Existing senior-review and
application-subtraction methods already preserve evidence and safety and need no
second checklist. The follow-up below extends component authoring across domains;
it does not require edits to Shinatama or make it a dependency.

## Approaches

The user accepted integration into existing owners after reviewing the alternative
of placing the coding guidance in Shinatama. A separate local Ponytail plugin
would create a competing source for discipline already owned by the harness.
Use original local instructions inspired by the external method, without copying
or vendoring its prompt, hooks, modes or dashboard. The intake policy permits
original inspiration with provenance.

## Behavior

- Prefer suitable project code and conventions, platform/stdlib, available
  dependencies, then the minimum new code. Explain exceptions by fit and total
  complexity. Existing dependency verification remains binding.
- Retain boundary validation, data protection, security and accessibility.
- Trace all required callers and supporting files before approving scope. Repair
  a shared cause; return newly required paths to planning before editing them.
- Existing projects keep their architecture and toolchain unless the task needs
  them changed. TypeScript loads the same common discipline as Python and declares
  its protocol and testing providers.
- Select checks by introduced failure modes and reuse existing protection. Avoid
  test quotas. Deliver saved test paths and actual verification evidence once.

The common protocol reaches isolated workers; lifecycle carries that discipline
in its briefs. The implementation roles load the canonical providers. No new
skill, command, runtime configuration or host mechanism is needed.

## Component-authoring propagation

The user extended the requirement to new skills, agents, tools and guidance for
other languages, frameworks and activities. Project-protocol owns this generic
authoring rule. The repository bootstrap, native intake/refresh methods and
project-knowledge's instruction planning point to that owner.

Authors apply the rules and provide an explicit consumption path for produced
components: a declared canonical provider, a required caller brief or a concise
domain adaptation for independent delivery. Executable helpers express applicable
obligations through contracts, protections and checks, with execution guidance in
their owning skill. Non-software activities retain their own observable outcomes
and evidence requirements. The rules do not force software testing onto them.

Trace the consumption path through references and worker briefs and preserve
required-provider recovery. Structural parity, behavioral execution and measured
efficiency remain distinct claims. This adds no command or new runtime mechanism.

## Acceptance and verification

The affected kernels and generated packages must reproduce for Claude, Codex,
Copilot, Pi and OpenCode. Required dependency, bundled-path, host-vocabulary,
registration, fact-anchor, instruction/document parity and repository test checks
run on the candidate. Review compares against captured pre-edit bytes because
the checkout contains unrelated work. No commit or push is part of this approval.

Behavioral scenarios live in `evals/project-protocol/minimal-complete-change.md`.
Their observable outcomes are separate from compiler checks; adding scenarios or
passing structural checks does not establish agent effectiveness or token savings.
