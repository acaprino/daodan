# A fifth host: the OpenCode V2 adapter

## 1. Goal

Compile every Daodan kernel into a fifth native package, `exports/opencode/`, installable
into [OpenCode](https://opencode.ai/) **V2** with one command, from the terminal and from
OpenCode Desktop alike, and with no hand-written file under `exports/`.

OpenCode V1 is out of scope, by decision. V2 rewrote the plugin API, the agent schema, the
permission model and the MCP configuration shape, so a dual-compatible package would carry
two implementations of every registration path for a line the vendor is replacing.

## 2. What OpenCode V2 is, and the six facts that shape the port

Established from the V2 documentation (`opencode.ai/v2/docs/`) and from the source of
`anomalyco/opencode` at tag `v2.0.22`, on 2026-10-02. `@opencode/cli@2.0.22` is the npm
`latest`; the `opencode-ai` package is still the V1 line.

1. **There is no marketplace and no static package format.** A package reaches OpenCode
   only as a *plugin*: an ES module whose default export is `{ id, setup }`. The service
   resolves it from the package's `main` (`packages/plugin/src/host.ts`). Installation is
   `opencode plugin add <spec>`, which accepts npm names, `github:` shortcuts, git URLs,
   tags, full commit hashes and npm's `::path:` repository-subdirectory selector.
2. **Skills, agents and commands in a plugin are registered from code.** Directory
   discovery (`skills/`, `agents/`, `commands/`) applies only to the config directories
   (`~/.config/opencode/`, `.opencode/`). A plugin contributes through transform hooks:
   `ctx.skill.transform`, `ctx.agent.transform`, `ctx.command.transform`,
   `ctx.mcp.transform` (`packages/plugin/src/promise/`).
3. **Subagents are native.** An agent with `mode: subagent` runs in a fresh child session
   through the built-in `subagent` tool, in the foreground or with `background: true`
   (`core/src/tool/plugin/subagent.ts`). No companion package is needed, unlike Pi.
4. **A command is an `execute` function, not a template.** `CommandDefinition` is
   `{ name, description?, execute }`. Template expansion of `$ARGUMENTS` and `$1..$n` lives
   in the core's config-command plugin (`core/src/config/plugin/command.ts`) and is not
   exported, so a plugin that ships prompt templates must expand them itself.
5. **IDs are free strings.** V2 does not enforce the kebab-case pattern it recommends for
   skills, and the core already registers commands with a colon in the name
   (`mcpCommandName` returns `server:prompt`). The skill schema is
   `{ id, name, description?, autoinvoke?, path, content }`; `autoinvoke: false` keeps a
   skill loadable but out of the model's list.
6. **Desktop is the same runtime.** OpenCode Desktop is an Electron shell that bundles the
   V2 CLI and runs `opencode serve --service`, adopting an already running compatible
   service (`packages/desktop/src/main/service/background-service.ts`). Config, plugins,
   skills, agents and commands are all loaded by that service, so a plugin installed for
   the CLI is the plugin Desktop sees. Desktop's own GUI extensions
   (`@opencode/gui-extensions`) are a different surface and are out of scope.

## 3. Decisions taken in the brainstorm

1. **Distribution is a generated plugin package with a fixed loader.**
   `exports/opencode/` is one npm-shaped package: rendered content, a `package.json`, and an
   `index.js` loader. Install:

   ```bash
   opencode plugin add 'github:acaprino/daodan#v<metadata.version>::path:exports/opencode'
   ```

   The `::path:` selector keeps the repository-root `package.json` exactly what it is today,
   Pi's catalog. Pinning and `opencode plugin update` come from the release tags
   `publish-marketplaces.yml` already writes.

2. **The loader is a fixed file driven by data, never generated code.** `index.js` lives in
   `adapters/opencode/templates/` and is copied verbatim. Everything plugin-specific (IDs,
   descriptions, file paths, permissions, dependencies, MCP commands) is computed by the
   compiler in Python and written into the package manifest. The toolchain stays
   standard-library Python, and the drift gate covers the loader and the data it reads
   like every other generated byte.

3. **Names follow Claude, not Pi.** Workflows register as `<plugin>:<workflow>`, roles as
   agents `<plugin>:<role>`, skills as `<plugin>:<skill>`. The kernels already write those
   references (`senior-review:code-auditor` 12 times, `senior-review:review-quality-gates`
   14 times), so they resolve as written. Pi needed the hyphen form because there the
   command name is a filename; registration from code has no such constraint.

4. **Per-plugin selection is in scope, and dependency closure overrides it.** See 5.2.

5. **No V1 compatibility.** See section 1.

6. **No name is shared across component kinds inside a plugin, and the kernels are
   renamed to make that true.** See section 7. On OpenCode skills and agents share one
   `@` mention menu, so a skill and a role of the same name become two identical
   `@<plugin>:<name>` entries that insert different things. The rename happens in the
   kernel rather than on this host alone, because decision 3 depends on a body's
   reference resolving as written on every host.

## 4. The adapter: `adapters/opencode/`

### 4.1 `capabilities.toml`

V2's built-in tools are `read`, `write`, `edit`, `patch`, `glob`, `grep`, `shell`,
`webfetch`, `websearch`, `skill`, `subagent` and `question`.

| capability | state | strategy | note |
|---|---|---|---|
| `repository.read` | native | tool `read` | |
| `repository.write` | native | tool `edit` | |
| `shell.execute` | native | tool `shell` | |
| `network.fetch` | native | tool `webfetch` | |
| `contexts.isolate` | native | `packaged-subagent` | agents registered by the loader, run by the `subagent` tool |
| `roles.dispatch` | native | `named-agent` | |
| `execution.parallel` | native | `concurrent-dispatch` | `background: true` |
| `tasks.share` | unsupported | none | |
| `peers.message` | unsupported | none | |
| `hooks.lifecycle` | unsupported | none | V2 has plugin runtime hooks, no probe has measured them, and no plugin requires this capability |
| `mcp.servers` | adapted | `mcp-manifest` | the compiler writes the per-plugin `.mcp.json` it already writes for Claude, and the loader registers it through `ctx.mcp.transform`; `adapted` because the host does not read the file, the loader does |

Every row is provisional until the probe in section 10 records evidence, which is the
standing rule for `adapters/*/capabilities.toml`.

### 4.2 `coordination.toml`

Two strategies, mirroring Copilot: `parallel-subagents` then `serial-isolated`, both
`availability = "baseline"`, `isolated = true`, `role_delivery = "named-agent"`. There is no
runtime-optional branch, because isolation is native.

### 4.3 `layout.toml`

```toml
[layout]
root = "exports/opencode"
marketplace = "exports/opencode/package.json"
plugin_root = "plugins/${plugin}"
skills = "skills/${skill}/SKILL.md"
roles = "agents/${role}.md"
role_template = "agent.md.tmpl"
workflows = "commands/${workflow}.md"
team_workflow_template = "team-command.md.tmpl"
package_files = "index.js"

plugin_root_reference = "<plugin-root>"
plugin_root_note = "`<plugin-root>` names this plugin's directory inside the installed package, the one that holds its `skills/`, `agents/` and `commands/`. The loader substitutes it in every body it registers; in any other file, resolve it once from where that file was loaded."
arguments_reference = "$ARGUMENTS"
workflow_frontmatter = "description, argument-hint"
```

Load-bearing details. `plugin_manifest` is absent: the package has one manifest, at its
root. `arguments_reference` maps onto itself with no note, because the loader expands
`$ARGUMENTS` with the core's semantics. `package_files` is new (section 6).

### 4.4 `templates/`

- `agent.md.tmpl`, bound to `role_template`. V2 agent frontmatter: `description`,
  `mode: subagent`, and `permissions` as an ordered rule list. The file is readable on its
  own and is valid in a V2 config directory, but the loader reads the metadata from the
  manifest and only the body from the file.
- `team-command.md.tmpl`, bound to `team_workflow_template`. It carries the generated
  dispatch plan like every other host, plus the OpenCode mechanism: dispatch each worker
  with the `subagent` tool, `agent: "<plugin>:<role>"`, `background: true` for workers of
  the same phase under `parallel-subagents`, and wait for every completion notice before
  closing the phase. Isolation is native, so there is **no** missing-tool branch: a
  `subagent` failure on a registered agent is a broken install, reported and stopped, the
  same rule as "Agent type not found" everywhere else.
- `index.js`, the loader, bound to `package_files`.

## 5. The loader

One ES module, no dependency (not `@opencode/plugin`, not `effect`), default export
`{ id: "daodan", setup }`. `setup(ctx)` does six things in order.

### 5.1 Read the manifest

It reads the `daodan` key of the `package.json` beside it. If the file is missing or does
not decode, it logs one `[daodan]` error and registers nothing. It never throws out of
`setup`, because one plugin failing setup can take down the whole V2 plugin generation,
providers included.

### 5.2 Resolve the selection

From `ctx.options`, set through the object form of a `plugins` entry:

```jsonc
"plugins": [{
  "package": "github:acaprino/daodan#v29.0.0::path:exports/opencode",
  "options": { "plugins": ["senior-review", "codebase-xray"] }
}]
```

- No options: every plugin.
- `plugins`: that set **plus its transitive closure over local dependencies**, read from
  the manifest. Each plugin pulled in that way is logged once.
- `exclude`: removes a plugin only when no selected plugin depends on it; otherwise it
  stays and the log says why. The repository's dependency policy (every internal
  dependency is mandatory) outranks the preference, and the log is where that is visible.
- An unknown name in either list is logged as an error and ignored, so a typo does not
  switch the marketplace off.
- Cross-marketplace dependencies (`superpowers@...`, `playwright@...`) are not the
  loader's concern: their stop-and-install blocks in the bodies apply unchanged.

### 5.3 Skills

One `ctx.skill.transform`, one `draft.add` per skill: `id` `<plugin>:<skill>`, `name` the
kernel frontmatter name, `description`, `path` the absolute `SKILL.md`, `content` the body
without frontmatter and with `<plugin-root>` substituted. Each `add` runs in its own
`try`, so a rejected skill skips itself and nothing else.

### 5.4 Agents

One `ctx.agent.transform`, `update(id, agent => ...)` per role, which creates the agent if
it does not exist (`core/src/agent.ts`): `mode = "subagent"`, `description`, `system` the
body with `<plugin-root>` substituted, `permissions` from the manifest. `model` is omitted,
because `inherit` is V2's default for a subagent. `color` is omitted, because the kernels
use names and V2 takes hex values, and a translation table is not worth maintaining.

The compiler derives `permissions` from the role's `tools` frontmatter with the same
name map that serves Copilot: `Read`/`Glob`/`Grep` to `read`/`glob`/`grep`,
`Write`/`Edit` to `edit`, `Bash` to `shell`, `WebFetch`/`WebSearch` to
`webfetch`/`websearch`, `Agent`/`Task` to `subagent`, always `skill`. The list starts with
`{ action: "*", resource: "*", effect: "deny" }` and appends one `allow` per mapped tool.
A role with no `tools` line gets no deny rule and inherits the defaults.

The last matching rule wins, so that leading deny also catches `external_directory`, and
the installed package lives outside the project (in OpenCode's package cache). A role
would then be refused the very skill references its body tells it to read. Every
permission list therefore ends with
`{ action: "external_directory", resource: "<package-root>/**", effect: "allow" }`,
which the loader substitutes with the absolute package path. The rule is scoped to the
package, never to `*`.

### 5.5 Commands

One `ctx.command.transform`, `add({ name, description, execute })` per workflow.
`execute` reads the template from disk at every invocation, substitutes `<plugin-root>`,
expands arguments with the core's semantics (quotes group and are removed, the highest
positional consumes the rest, missing positions become empty, and with no placeholder the
arguments are appended after a blank line), then calls
`ctx.session.prompt({ ...input.prompt, sessionID: input.sessionID, text, delivery: input.delivery })`.

The core's `` !`shell` `` blocks are **not** implemented: no kernel uses them, and a test
keeps that true (section 9). The two `docker-compose` lines found in kernels sit inside
fenced code the agent runs, not in template syntax.

### 5.6 MCP

For each selected plugin that declares a server, today only `peer-review`, the loader reads
the server from the manifest (the same data the compiler writes to that plugin's `.mcp.json`) and calls
`ctx.mcp.transform(editor => editor.set(name, { type: "local", command: [command, ...args] }))`
with `<plugin-root>` substituted. A server name the user already configured is left alone
and logged, never overwritten.

### 5.7 What the loader does not do

No runtime hooks, no injected bootstrap, no custom tools, no V1 export.

## 6. Compiler changes

1. `HOSTS` gains `"opencode"`, and the partial-publication refusal names five hosts.
2. A new optional layout key, `package_files`: files copied verbatim from the adapter's
   `templates/` to the layout root, once per build rather than once per plugin.
3. `render_catalog` gains an OpenCode serialization: the package `package.json`
   (`name: "daodan"`, `version` from `metadata.version`, `private: true`,
   `type: "module"`, `main: "index.js"`, `keywords: ["opencode-plugin"]`) with a `daodan`
   key carrying, per plugin, its local dependencies and its registered components with
   everything 5.3 to 5.6 need. The neutral document `assert_cross_host_identity` compares
   is unchanged, exactly as for Pi.
4. Role permissions for OpenCode are derived beside `_copilot_tools`, sharing its name map
   so the two cannot drift.
5. `_source` returns `./plugins/<name>`, relative to the package root, for this host.

No override. The only kernel changes are the renames in section 7.

## 7. Renaming the five homonyms

A census of the kernels at marketplace 28.7.x found five names shared across kinds inside
one plugin:

| plugin | name | kinds | collides on OpenCode |
|---|---|---|---|
| abstraction-architect | `abstraction-architect` | skill, role | yes: both are `@` mentions |
| browser-extensions | `firefox-extension-dev` | skill, role | yes |
| digital-marketing | `brand-naming` | skill, workflow | no: `@` against `/` |
| digital-marketing | `reply-to-customer-review` | skill, workflow | no |
| python-development | `python-refactor` | skill, workflow | no |

The first draft of this spec gave `codebase-xray:analyze` as an example. That was wrong:
its skill is `xray-method`.

All five are renamed, the last three too, so the rule below holds without exceptions.

**Roles take the `-agent` suffix**, the existing convention for a role beside a
same-topic skill (`python-refactor-agent`, `clean-code-agent`):

- `abstraction-architect:abstraction-architect` becomes
  `abstraction-architect:abstraction-architect-agent`
- `browser-extensions:firefox-extension-dev` becomes
  `browser-extensions:firefox-extension-dev-agent`

**Skills, not workflows, take the `-method` suffix in the skill/workflow pairs.** A command
is what a user types and what the documentation's examples show; a skill is found by the
model through its description and named only in cross-references. `codebase-xray` is the
precedent: skill `xray-method`, workflow `analyze`. The skill is the method, the workflow
is the action.

- `digital-marketing:brand-naming` (skill) becomes `brand-naming-method`
- `digital-marketing:reply-to-customer-review` (skill) becomes `review-reply-method`
- `python-development:python-refactor` (skill) becomes `python-refactor-method`

The three commands keep their names: `/digital-marketing:brand-naming`,
`/digital-marketing:reply-to-customer-review`, `/python-development:python-refactor`.

What does **not** move:

- The `.python-refactor/` run-state directory and the `.abstraction-architect/` concept
  index. Those are artifact paths, not component names, and renaming them would orphan
  existing runs.
- The plugin names. Every occurrence of `abstraction-architect` that names the plugin (its
  `plugin.toml`, `senior-review`'s dependency list, the dependency-graph linter's edge, the
  test clusters) stays as it is; only the role reference changes.
- Codex's `-workflow` suffix. The new rule makes it unnecessary, but removing it would
  rename every Codex workflow skill a user already has installed, which this change does
  not need.

**Rename footprint**, measured: the role and skill directories and files themselves, their
frontmatter `name`, the `[components]` lists of the three `plugin.toml` files, the `role =`
line of `abstraction-architect/workflows/audit.toml`, the role references in
`senior-review`'s `code-auditor`, `code-review`, `team-review` and
`code-review-agents.md`, the three `firefox-*` workflows and their sidecars, the
"Invoke the `<name>` skill" lines of the two digital-marketing workflows, the skill
cross-references in `clean-code-agent`, `python-refactor-agent`, `python-comments`,
`optimization-patterns.md`, `skills-vs-agents.md` and `organize-files.md`, and
`docs/plugins/{abstraction-architect,browser-extensions,digital-marketing,python-development,senior-review,text-humanizer}.md`.
Each occurrence is classified by hand as plugin, role, skill, workflow or artifact before
it is edited; a blanket replace would rename plugins and artifact paths.

**Versions**: `abstraction-architect`, `browser-extensions`, `digital-marketing`,
`python-development`, `senior-review`, `clean-code`, `marketplace-ops` and `system-utils`
each take a bump, because each kernel changes. A renamed role or skill is a breaking
change for anyone who spawns or loads it by name, so the two role renames and the three
skill renames take a **major** bump of their owning plugin; the plugins whose only change
is a cross-reference take a patch.

**The guard**: a new validation rule in `scripts/daodan/validate.py`,
`component-name-shared-across-kinds`, fails the build when any name appears in more than
one of a plugin's `skills`, `roles` and `workflows`. It is what keeps this from returning,
and it applies on every host, not only OpenCode.

## 9. CI and tests

- `tests/test_opencode_loader.py` runs `node --test` over
  `tests/opencode/loader.test.mjs` against a fake `ctx`, and skips when `node` is absent.
  It covers selection and closure, `exclude` yielding to a dependency, a malformed
  manifest registering nothing without throwing, one rejected skill not stopping the
  others, argument expansion case by case against the core's semantics, `<plugin-root>`
  substitution, and an existing MCP server left alone. GitHub's runners carry Node, and
  both workflows run it.
- OpenCode assertions in `tests/test_daodan_host_rendering.py`: colon IDs in the manifest,
  `$ARGUMENTS` intact, the deny-then-allow permission list, the dispatch plan naming the
  `subagent` tool, and no `` !` `` in any rendered command body.
- `scripts/lint_plugin_registration.py` checks the `daodan` key both ways against the
  generated tree, like the enumerating hosts.
- `tests/host-probes/opencode/`, packaging the same `daodan-probe` fixture, registered in
  `scripts/probe_host_marketplaces.py`.
- `publish-marketplaces.yml` adds `exports/opencode` to the committed paths.
- `tests/test_daodan_validate.py` gains the `component-name-shared-across-kinds` cases: a
  skill and a role, a skill and a workflow, a role and a workflow sharing a name each
  fail, and the real kernels pass.
- The test files that name four hosts are updated to five.

## 10. What the probe must confirm

Every capability row in 4.1 and every naming decision in section 3 is provisional until
then.

1. That `opencode plugin add` with `github:...#tag::path:exports/opencode` installs and
   loads the package, on the CLI and in Desktop.
2. That a skill with ID `senior-review:review-quality-gates` loads through the `skill`
   tool, and that `subagent` dispatches an agent named `senior-review:code-auditor`.
   **If either fails**, that kind falls back to the hyphen form Pi uses
   (`senior-review-code-auditor`) through `layout.toml`, and the kernel references to that
   kind get rewritten by the renderer the way `${CLAUDE_PLUGIN_ROOT}` is.
3. That a registered skill appears only in the `@` mention menu and never in the `/`
   command catalog, which is what the 2.0.22 TUI source shows
   (`packages/tui/src/component/prompt/autocomplete.tsx` lists skills and agents under `@`,
   server commands under `/`). The renames in section 7 make every ID unique within a
   plugin whatever the answer, so this item can no longer produce a collision, only a
   cosmetic duplicate listing.
4. That `background: true` workers of one phase actually run concurrently.
5. That a git-backed spec installs on Windows. Superpowers documents failures there under
   V1 and Bun; V2 has a new npm service no one has measured.

## 12. Out of scope

OpenCode V1, Desktop GUI extensions, runtime hooks, an injected bootstrap, custom tools,
the `` !`shell` `` template syntax, npm publication of the package, any override, any
hand-written file under `exports/`, and removing Codex's `-workflow` suffix.
