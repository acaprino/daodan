# moe

Ultra Nerd is an explicit, bounded multi-model deliberation workflow for difficult
problems. Two distinct configured models first propose independently, then exchange
attributed critiques. The coordinator verifies decisive claims and delivers one
answer with evidence and remaining disagreements.

The required peer-review plugin supplies its independence doctrine. MoE has its own
MCP server with moe_models and moe_ask. This workflow has its own delivery contract and does not claim peer-review
certification. Increased token usage is disclosed before paid calls. Defaults are
two rounds, at most six invocations, 4096 output tokens per request and 24000 UTF-8
bytes per payload. These do not guarantee a total billing cap.

The host owns execution, enforceable budgets and cancellation. Tri-Tech chat UI,
Gateway-only profile binding and relocated transport paths require consumer work.
Compilation of all hosts establishes registration and adapted content, not a live
model exchange.


The 24000-byte reciprocal payload reserves 6000 UTF-8 bytes for the brief, 8000
for each exact reply and 2000 for framing. Oversized briefs stop before spending.
In managed mode (`brief` / `run_id`), the MCP server automatically creates
`<run_root>/<run_id>/` on the first proposal, writes `brief.md` and `exchange.json`,
binds the second proposal's `peer_model` to the first returned model identity, and
composes reciprocal critique payloads with both previous-round replies and pinned
`expected_model` / `peer_model` identities. Collisions, missing identities or model
changes stop the run and mark `exchange.json` as `failed`. Low-level `content_path`
calls remain supported as well. Payloads are read using pinned nonlink directory/file
handles, not a checked path that is reopened without protection.

## Launch isolation

The server starts as `uv run --no-config --no-project --script` on the bundled
`server.py`. The two flags keep `uv` from reading the current project's `uv.toml`,
`pyproject.toml` or `.python-version`: the server runs inside the user's project
and holds the gateway key, so that project must never choose the package index or
interpreter the server's `mcp` dependency is installed from. Keep both flags in any
manual registration.

## Failure contract

Every refusal or failure of `moe_ask` returns `error`, `code` and `charged`.
Before this contract, four unrelated causes (a reply over its byte reservation,
a finish reason the transport did not recognize, a reply made of tool calls, and
a network failure) collapsed into one generic message, and a coordinator could
not tell whether to narrow the brief, raise the output limit or stop. The codes
are `invalid_request`, `identity_contract`, `model_collision`, `payload_invalid`,
`brief_bound`, `transport`, `response_shape`, `model_identity_missing`,
`model_changed`, `reply_tool_calls`, `reply_empty`, `reply_truncated`,
`finish_reason_unsupported` and `reply_bound`. `charged` is false when nothing
was sent and true once a paid request had left, so partial spending is reported
rather than guessed.

A gateway that forwards a provider's own vocabulary is accepted: `end_turn` and
`stop_sequence` count as complete, an absent finish reason is reported as
`unknown`, and `length` or `max_tokens` is `reply_truncated`. The reply bound is
the cause a workflow meets most often, because 4096 output tokens can be twice the
8000-byte reservation; the workflow therefore states the ceiling in words.
