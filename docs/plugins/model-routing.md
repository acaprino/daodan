# Model routing

Select the model and effort for each LLM job from measured host availability, task signals and catalog evidence, with explicit confirmation before binding.
The dependency-free plugin also owns model catalog refresh, price rules and host usage pricing.

For each DAG node, job or process that calls an LLM, the coordinator follows
[deterministic request routing](../../plugins/model-routing/skills/model-routing/references/task-routing.md)
before dispatch. Each request identifies the node, role, objective, relevant
input/context digests, capabilities and risk; the classifier describes that
work and `task_router.py` selects its model. Deterministic nodes need no model.
Bindings are request-keyed and require human confirmation. The root model is
not a DAG-wide assignment: a `node_id` binding map, automatic dispatcher
consumption and a run-wide automatic approval policy remain future integration.

Capabilities have one vocabulary, `scripts/model_capabilities.py`: six features
(tool call, reasoning, attachment, structured output, temperature, interleaved
reasoning) and text, audio, image, video and PDF on each side. The catalog
builder, both routers and the OpenRouter harvester read every model entry
through it, so each exposes the same capabilities under the same names. A
capability the request's inputs need, such as an attached video, is named by
the caller with `--require`; the host's inventory gates it, and a catalog that
disagrees with the host about the chosen model is reported.
