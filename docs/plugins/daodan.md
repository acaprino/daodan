# Daodan

The entry plugin: one command per intention, and no parameters. Every core
specialist plugin keeps its skills, roles and contracts and has no command of its own;
independent domain verticals keep their own workflow namespaces. Each command here
is a thin entry into the canonical method of its owner,
usable alone or as a step of the task cycle. These commands are the primary
surface for project work; a domain vertical's own command is the direct route
once the request is already specific to that domain. The only argument is free text,
read as a path, a commit, a pull request or a branch when one exists, and as
text otherwise; the command says how it read it before starting.
Authorizations are asked when a step needs them, once, and recorded in the run.

| Group | Command | What it does |
|---|---|---|
| Project | `init-project` | First-use analysis depth, map, verified environment and commands, loop block, test baseline; approves the specification before scaffolding projects without application code, reusing prior design and choices |
| | `onboard-project` | A dossier for whoever takes the project over; changes nothing |
| | `check-health` | Read-only diagnosis of structure, tests, documentation, workspace and each stack, with a plan |
| | `run-maintenance` | The guided campaign, stage by stage |
| Thinking | `brainstorm-idea` | Clarifies intent, writes a specification in `docs/specs/`, obtains approval, then builds when authorized or keeps the design |
| | `investigate-problem` | Facts, perimeter, isolated hypotheses, reproduction test, bisection; never fixes |
| | `get-second-opinion` | Another model challenges a file, or several deliberate a question, after consent |
| Working | `new-feature` | The task cycle: interview, specification reviewed and approved, plan in waves, execution, light review per commit |
| | `fix-bug` | Reproduction test first, then the fix; investigates first when the cause is unknown |
| | `refactor-code` | Characterization tests, structural oracles, behavior unchanged |
| | `continue-task` | Resumes the branch's task from any session; its text answers pending questions |
| | `show-status` | The agenda, branches, map freshness and records; changes nothing |
| | `finish-task` | Branch review, merge with authorization, record verified when there is one, knowledge realigned, worktree removed |
| | `sync-upstream` | Fetch, report, fast-forward only, realign |
| Review | `review-changes` | Light review: the project's tools, then one reviewer chosen by the target's kind |
| | `review-branch` | Complete review of a branch or pull request, its roster computed from the diff and the map |
| Tools | `write-tests` | Tests for named code, in the project's framework and layout |
| | `map-code` | The lite map when none exists, then the cards an area lacks |
| | `write-docs` | Drift audit and correction, or the guide, README or instructions asked for |
| | `record-decision` | A decision record outside a task, accepted on your approval before any code; turns records on for a project without them |
| | `tidy-repo` | Workspace, dead code, redundant tests, concluded run output: preview, then one authorization |
| | `humanize-text` | Natural prose without invented content |

On Claude Code and OpenCode a command is `/daodan:<name>`; on Pi it is
`/daodan-<name>`; on Codex it is the skill `<name>-workflow`; on Copilot it is
the prompt `<name>` with its `<name>-coordinator` agent. The names are verbs
so that none collides with a host's built-in command (`/review` on Codex,
`/init` and `/docs` on Claude Code).

The design, the mapping from the 32 commands it replaced and the reasons are in
[the command set design](../superpowers/specs/2026-10-19-command-set-design.md).
