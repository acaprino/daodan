# ADR-0004: Version decision records in place and check what a change invalidates

## Context and Problem Statement

A decision record is read at every step of the task cycle: the interview
inherits it, every worker brief carries its examples and invariants, every
review receives them as the intent of the change. The helper
`plugins/project-knowledge/skills/adr-method/scripts/adr_tool.py` keeps the
directory consistent and promotes records atomically. Six gaps, found while
comparing it with ruflo-adr on 2026-10-24 and while writing
`docs/decision-records.md`:

1. Changing one invariant of an `Accepted` record needs a new record with a new
   identity that restates the whole decision; `supersedes` is the only
   relation. Citations in code and in the loop block then point to a
   `Superseded` record.
2. `status.md` and `realign.md` of `lifecycle-method` promise a list of active
   records whose governed code changed. Nothing computes it; `last_verified_sha`
   is written once, at promotion.
3. `adr-method/SKILL.md` retires an abandoned `Proposed` record by superseding
   it, which `adr_tool.py` refuses: a `Proposed` record stays `Proposed`
   forever.
4. Records depend on one another only in prose: ADR-0003 cites ADR-0002, and a
   change of ADR-0002 names nothing to re-read.
5. Version, state, date and author are visible only in YAML.
6. A record becomes `Accepted` at the merge of its implementation, which mixes
   approving a decision with realizing it.

Since ADR-0005, all of this applies only to a project that keeps records.

## Decision Drivers

- A cheap model reads one record per decision, never two to merge.
- Identities cited in code and in other records survive a change of the
  decision.
- A decision rests on the text the user read; no write replaces bytes that
  changed since that read.
- One check per risk, and no flag that only restates what the helper can
  compute.
- The helper guarantees shape mechanically; reviewers judge content.

## Decision

- **Acceptance is approval.** `Proposed` waits for the user's approval;
  `Accepted` means the user approved this exact text, whether its code is
  absent, in progress or present. `promote --adr ADR-NNNN --sha SHA
  --expect-digest D` records it, `D` being the digest of the text the user was
  shown. `accepted_at_sha` is the commit at approval, never evidence of
  implementation, and `last_verified_sha` stays empty until `verify`. Approval
  creates and authorizes no work; a merge never approves.
- **Versions.** The front matter gains `version`, an integer from 1.
  `propose --revise ADR-NNNN --body FILE` writes `ADR-NNNN-v<N>-<slug>.md` as
  `Proposed`; the helper numbers it and records in `changes` the item
  identities whose text differs from the `Accepted` version. A decision has at
  most one `Proposed` version. Its `promote` marks the previous version
  `Superseded` in the same transaction, and `resolve` returns only the
  `Accepted` version. `supersedes` stays for a different decision. A citation
  `ADR-NNNN` means the active version; `ADR-NNNN v1` pins one.
- **One concurrency check.** `validate --adr` and `resolve` print each record's
  `digest`, the SHA-256 of its file. Every command that rewrites an existing
  record (`promote`, `verify`, `retire`) takes `--expect-digest`, holds an
  exclusive lock under `docs/adr/` and refuses, writing nothing, when the
  record's current digest differs. The index is regenerated from the records
  under the same lock, so it needs no check of its own.
- **Header.** Under the title the helper renders version, status, date and
  author (the Git identity at `propose`), regenerated by every write. Nobody
  edits it.
- **Drift.** `validate --sha SHA` adds `drifted`: each `Accepted` record whose
  `scope.paths` or `governs_symbols` files changed since `last_verified_sha`
  (`git diff --name-only`), with those files, or with `files: null` when it was
  never verified. `verify --adr ADR-NNNN --sha SHA --expect-digest D` sets
  `last_verified_sha` after a reviewer confirmed the code conforms. This is the
  list `status.md` and `realign.md` promise; the branch review receives
  `resolve --paths <changed files>`.
- **Retirement.** `retire --adr ADR-NNNN --reason TEXT --expect-digest D`
  moves a `Proposed` record to `Abandoned`; `resolve` ignores it and nothing
  leaves it.
- **Dependencies.** `propose --depends-on ADR-NNNN...` records `depends_on`,
  each an `Accepted` decision. When `promote` supersedes a decision or a
  version that others depend on, its output lists them as
  `dependents_to_review`; the cycle records each as an open question of the
  run. The helper never rewrites a dependent.

The new surface is six items: `--revise`, `--expect-digest`, `--depends-on`,
`--sha` on `validate`, `verify` and `retire`.

## Verified Interview Examples

- **EX-001** (nominal case): Input: `ADR-0006 v1` is `Accepted`; `propose --revise ADR-0006 --body B`, where `B` changes only `INV-001` -> Expected: `docs/adr/ADR-0006-v2-<slug>.md` written as `Proposed`, `version: 2`, `changes: ["INV-001"]`.
- **EX-002** (nominal case): Input: the user approves v2 shown with digest `D`; `promote --adr ADR-0006 --sha A --expect-digest D` before any implementation -> Expected: v2 `Accepted` with `accepted_at_sha: A` and an empty `last_verified_sha`, v1 `Superseded`, `resolve` returning only v2.
- **EX-003** (rejection case): Input: after the approval another session rewrites v2 (digest `D2`); the same `promote` -> Expected: refused, "ADR-0006 v2 changed since it was read: expected D, found D2", every file and the index unchanged.
- **EX-004** (rejection case): Input: `propose --revise ADR-0006` while v2 is still `Proposed` -> Expected: refused, one open version per decision, nothing written.
- **EX-005** (boundary case): Input: v2 verified at `S1`; `src/orders/validator.py` in its `scope.paths` changed by `S2`; `validate --sha S2` -> Expected: `drifted: [{"adr_id": "ADR-0006", "version": 2, "files": ["src/orders/validator.py"]}]`; after `verify --adr ADR-0006 --sha S2 --expect-digest D3`, `drifted: []`.
- **EX-006** (boundary case): Input: right after EX-002, `validate --sha A` -> Expected: `drifted` lists `ADR-0006` v2 with `files: null`; the approval commit is never used as a verification baseline.
- **EX-007** (nominal case): Input: `ADR-0003` has `depends_on: [ADR-0002]`; `promote` of a record that supersedes `ADR-0002` -> Expected: output carries `dependents_to_review: ["ADR-0003"]`, and `ADR-0003` stays byte-identical.
- **EX-008** (nominal case): Input: `retire --adr ADR-0001 --reason "replaced by the decision map" --expect-digest D` on a `Proposed` record -> Expected: `Abandoned`, listed under its own heading of the index, never returned by `resolve`; a later `promote` of it is refused.
- **EX-009** (rejection case): Input: `propose --revise ADR-0006 --supersedes ADR-0006` -> Expected: refused, a version never supersedes its own decision.
- **EX-010** (boundary case): Input: the user approves a record in a decision-only conversation and defers implementation -> Expected: `Accepted`, empty `last_verified_sha`, no task created, no code edit, commit or merge authorized.

## Rejected Alternatives

- **RA-001**: an `amends` relation whose items `resolve` merges into an `Accepted` record; rejected because the model would read two records for one decision or trust a merge done by the helper.
- **RA-002**: dotted versions (`1.1`, `2.0`); rejected because nobody agrees on what a minor change is, and the helper numbers versions anyway.
- **RA-003**: editing an `Accepted` record in place; rejected because the approved text disappears.
- **RA-004**: acceptance at the merge of the implementation; rejected because it mixes approving a decision with realizing it, and a decision may be recorded before, during or after its code.
- **RA-005**: an approval reference beside the digest, a re-read before replacing, a read-back after writing and a digest of the index; rejected because under the exclusive lock the compared bytes are the bytes replaced, and the index is derived from the records: one check covers the risk.
- **RA-006**: `--replace ITEM TEXT`, `--version`, `--author` and `--evidence`; rejected because the model writes the new body anyway, the helper computes changes and numbers, the author is the Git identity, and evidence lives in the run.
- **RA-007**: warnings about dependencies repeated by every `validate`, or a promotion blocked until dependents are reviewed; rejected because one open question recorded at the promotion reaches the reviewer without noise or stops.
- **RA-008**: a separate `unverified` list and a header check in `validate`; rejected because `files: null` in `drifted` says the same, and a header nobody edits is rewritten by every write.
- **RA-009**: a database of record relations, as ruflo-adr's AgentDB; rejected as a second owner of facts the records hold.
- **RA-010**: superseding an abandoned `Proposed` record from a later one; rejected because a chain ending in a record that never held makes `supersedes` mean two things.

## Enforceable Invariants

- **INV-001**: a decision has at most one `Accepted` and one `Proposed` version, and `resolve` returns at most one record per decision.
- **INV-002**: a version after the first comes only from `propose --revise`, and `changes` lists exactly the items whose text differs from the `Accepted` version.
- **INV-003**: `Proposed` becomes `Accepted` only through `promote` with the digest of the approved text; a merge is neither required nor sufficient.
- **INV-004**: every command that rewrites an existing record holds the exclusive lock and refuses without writes when the record's digest differs from `--expect-digest`.
- **INV-005**: `drifted` comes only from `git diff --name-only <last_verified_sha> <sha>` against `scope.paths` and the files of `governs_symbols`, and an empty baseline is reported as never verified; the helper never judges conformance.
- **INV-006**: `Abandoned` is reached only from `Proposed` through `retire` with a reason, and nothing leaves it.
- **INV-007**: every write is atomic: the future state is validated before any file or the index is written.
- **INV-008**: `supersedes` names a different decision, `depends_on` names `Accepted` decisions and never the record itself, and the helper never rewrites a dependent.
- **INV-009**: an approval creates no task and grants no edit, commit or merge.

## Consequences

- `adr_tool.py` gains the six items above, the `version`, `changes`,
  `depends_on` and `retired_on` fields, the header renderer and the `Abandoned`
  state; `references/adr-template.md` documents them and the file name
  `ADR-NNNN-v<N>-<slug>.md`, while v1 keeps its current name.
- `adr-method/SKILL.md` describes acceptance at approval, versions, the
  digest, drift, retirement and dependencies, and drops the
  supersede-a-`Proposed` rule.
- `lifecycle-method`: `interview.md` asks for approval and promotes on it;
  `finish.md` and `realign.md` call `verify` after the review instead of
  promoting at the merge; `status.md` and `realign.md` read `drifted` from
  `validate --sha`. `review-preparation` of `senior-review` feeds
  `resolve --paths` over the diff to the branch review.
- `work-controller`: the run's `adr` section accepts `ADR-NNNN vN`.
- `daodan`'s `record-decision` promotes on approval without waiting for code.
- `docs/decision-records.md` describes versions, approval, the digest, drift,
  retirement and dependencies.
- The existing `Proposed` records gain `version: 1` and a header; ADR-0003
  declares `depends_on: [ADR-0002]`.
- Versions bump `project-knowledge`, `project-lifecycle`, `work-controller`,
  `senior-review` and `daodan`, and the marketplace.
